# DeltaRent 项目核心技术与设计详解

> 三角洲行动账号租赁管理系统 —— 课程实践项目技术文档

## 一、项目总览

DeltaRent 是一个前后端分离的游戏账号租赁平台，围绕"三角洲行动"这款游戏，实现了账号浏览、租赁下单、订单管理、售后申诉和后台管理的完整业务闭环。

| 模块 | 技术栈 |
|------|--------|
| 前端 | Vue 3.5 + TypeScript + Vite 6 + Vue Router 4 + Pinia 3 + Element Plus 2.10 |
| 后端 | Spring Boot 3.3.5 + Spring Security + JWT (jjwt 0.12.6) + MyBatis 3.0.4 |
| 数据库 | MySQL 8（生产） / H2（开发与测试） |
| 构建工具 | npm / Vite（前端），Gradle Wrapper（后端） |
| 运行环境 | JDK 21，Node.js 20+ |

## 二、系统架构设计

### 2.1 整体架构

系统采用经典的**前后端分离**架构，前端和后端是两个独立运行的应用程序，通过 HTTP API 进行数据交互。

```
┌──────────────────┐       HTTP / JSON        ┌──────────────────────┐        SQL         ┌─────────┐
│   Vue 3 前端      │  ──────────────────────→ │   Spring Boot 后端    │ ─────────────────→ │  MySQL  │
│  (端口 5173)      │  ←────────────────────── │     (端口 8080)       │ ←───────────────── │         │
│  Vite 开发服务器   │       REST API           │  Spring Security      │                    │         │
└──────────────────┘                          └──────────────────────┘                    └─────────┘
```

**前后端分离的优势**：
- 前端专注于 UI 交互和用户体验，后端专注于业务逻辑和数据处理
- 前后端可以独立开发、独立部署、独立扩展
- 前端可以实现单页应用（SPA），页面切换无需刷新，用户体验更流畅

### 2.2 后端分层架构

后端采用经典的四层架构，各层职责清晰：

```
┌─────────────────────────────────────────────────────┐
│  Controller 层（控制器）                               │
│  接收 HTTP 请求，参数校验，调用 Service，返回响应        │
│  对外暴露 RESTful API 接口                            │
├─────────────────────────────────────────────────────┤
│  Service 层（业务逻辑）                                │
│  核心业务逻辑、事务管理、数据组装                        │
│  是整个系统最核心的一层                                 │
├─────────────────────────────────────────────────────┤
│  Mapper 层（数据访问）                                 │
│  使用 MyBatis 注解方式编写 SQL，操作数据库              │
├─────────────────────────────────────────────────────┤
│  Domain 层（实体）                                    │
│  Java 实体类，与数据库表一一对应                        │
└─────────────────────────────────────────────────────┘
```

这种分层设计的好处是**高内聚、低耦合**：Controller 不关心业务怎么算，只管收发请求；Service 不关心 SQL 怎么写，只管调 Mapper；Mapper 不关心业务规则，只管读写数据库。

## 三、数据库设计

### 3.1 ER 关系概览

数据库共 9 张表，围绕三条业务主线组织：

```
【用户线】                    【商品线】                  【交易线】
sys_user ──M:N── sys_role    rental_product             rental_order
     │                             ↑                        ↑
     └── sys_user_role             │                        │
                                   └──── 用户发布商品 ────────┘
                                                        appeal_record（售后申诉）

【辅助线】
notice（公告）、sms_verify_code（验证码）、operation_log（操作日志）
```

### 3.2 核心表结构

#### sys_user（用户表）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT PK | 主键 |
| username | VARCHAR(50) UK | 用户名，唯一 |
| phone | VARCHAR(20) UK | 手机号，唯一 |
| password_hash | VARCHAR(255) | BCrypt 加密后的密码 |
| nickname | VARCHAR(50) | 显示昵称 |
| status | TINYINT | 状态：1-正常，0-禁用 |
| password_updated_at | DATETIME | 密码最后修改时间，用于 JWT 版本校验 |

#### rental_product（租赁商品表）

这是字段最多的一张表，存储三角洲行动游戏账号的各项属性：

| 字段分类 | 关键字段 | 说明 |
|----------|----------|------|
| 基本信息 | name, category, tag_text | 名称、分类、标签 |
| 租赁信息 | price, deposit, rental_days | 租金、押金、租期 |
| 游戏属性 | coin_amount, rank_text, kd | 哈夫币、段位、KD值 |
| 装备属性 | insurance_box, stamina_level, weight_level | 保险格数、体力、负重 |
| 外观资源 | knife_skin_text, character_skin_text | 刀皮、干员红皮 |
| 状态控制 | status | PENDING/AVAILABLE/RENTED/MAINTENANCE/OFF_SHELF |

#### rental_order（租赁订单表）

| 字段 | 类型 | 说明 |
|------|------|------|
| order_no | VARCHAR(40) UK | 订单号，格式 DR + 时间戳 |
| user_id | BIGINT FK | 下单用户 |
| product_id | BIGINT FK | 租赁商品 |
| unit_price | DECIMAL | 下单时的租金快照（防止商品改价影响历史订单） |
| order_amount | DECIMAL | 订单总额 = 单价 × 时长 |
| deposit_amount | DECIMAL | 押金快照 |
| status | VARCHAR(30) | 订单状态，见下方状态机 |

### 3.3 数据库设计要点

**为什么用户和角色要分三张表（sys_user、sys_role、sys_user_role）？**

这是 RBAC（Role-Based Access Control，基于角色的访问控制）的标准设计模式。用户和角色是多对多关系——一个用户可以有多个角色，一个角色也可以属于多个用户。通过中间表 `sys_user_role` 关联，方便灵活扩展。系统中定义了三种角色：

| 角色 | 代码 | 权限范围 |
|------|------|----------|
| 管理员 | ADMIN | 全部权限：用户管理、商品管理、订单管理、公告管理、数据看板 |
| 普通用户 | USER | 浏览商品、下单、查看订单、提交申诉、发布账号 |
| 客服 | CS | 账号维护、订单状态管理、售后处理 |

**为什么订单要存 unit_price 快照？**

下单时把当时的租金记录到订单表里，即使商品后来改价，历史订单的金额也不会变。这是电商系统的常见设计。

## 四、核心设计一：JWT 认证系统

这是整个项目最核心的技术设计，实现了无状态的用户身份认证。

### 4.1 整体认证流程

```
                         ┌─────────────────────────────────────────────────────────┐
                         │                    认证流程全景                           │
                         └─────────────────────────────────────────────────────────┘

【登录阶段】
  用户输入手机号+密码
       │
       ▼
  UserService.login()
       │  ① 查数据库验证用户存在且状态正常
       │  ② 用 BCrypt 比对密码
       │  ③ 生成 JWT Token（含 userId, username, role, pwdUpdatedAt）
       │
       ▼
  返回 {token, user} 给前端 → 前端存入 localStorage


【请求认证阶段】（每个需要认证的请求都要走）
  前端发请求，Header 带 Authorization: Bearer <token>
       │
       ▼
  JwtAuthFilter（JWT 认证过滤器）
       │  ① 从 Header 提取 token
       │  ② 用密钥验签 + 检查有效期
       │  ③ 从 token 解析出 userId，查数据库拿最新用户信息
       │  ④ 对比 token 中的 pwdUpdatedAt 和数据库中的值
       │     （如果密码被改过，token 中的旧版本号不匹配 → 拒绝访问）
       │  ⑤ 验证通过 → 设置 SecurityContext，请求继续
       │
       ▼
  SecurityConfig（权限配置）判断该 URL 需要什么角色
       │
       ▼
  Controller → Service → Mapper → 数据库
```

### 4.2 JWT Token 的结构

JWT（JSON Web Token）由三部分组成，用 `.` 分隔：

```
Header.Payload.Signature

Header:   {"alg": "HS256", "typ": "JWT"}           → 算法和类型
Payload:  {"sub": "2", "username": "demo_user",     → 用户信息（载荷）
           "role": "USER",
           "pwdUpdatedAt": "2026-05-18T10:00:00",
           "iat": 1747574400, "exp": 1747660800}
Signature: HMAC-SHA256(Header + Payload, 密钥)       → 签名，防篡改
```

**签名的作用**：任何人修改了 Header 或 Payload，签名就会对不上，服务端验签时会失败。所以 token 虽然存在前端，但前端无法伪造或篡改。

### 4.3 密码版本校验机制

这是一个巧妙的安全设计。JWT 一旦签发，24 小时内都有效。但如果用户改了密码，旧的 token 应该立即失效。

实现方式：
1. 数据库 `sys_user` 表有 `password_updated_at` 字段，记录密码最后修改时间
2. 生成 token 时，把这个时间写入 token 的 `pwdUpdatedAt` 字段
3. 每次请求认证时，从数据库查最新的 `password_updated_at`，和 token 中的对比
4. 如果不一致，说明密码被改过了，token 失效

```java
// JwtAuthFilter.java 核心逻辑
String tokenPasswordVersion = claims.get("pwdUpdatedAt", String.class);
String currentPasswordVersion = JwtUtil.formatPasswordVersion(user.getPasswordUpdatedAt());
if (!safeEquals(tokenPasswordVersion, currentPasswordVersion)) {
    // 密码已修改，token 失效
    writeUnauthorized(response, "登录状态已失效，请重新登录");
}
```

### 4.4 Spring Security 权限配置

SecurityConfig 定义了 URL 级别的访问控制规则：

```java
// 完全公开，谁都能访问
.requestMatchers("/api/health", "/api/auth/**", "/api/portal/**").permitAll()

// GET 请求公开（游客能浏览商品和公告）
.requestMatchers(HttpMethod.GET, "/api/rentals", "/api/rentals/**").permitAll()

// 需要登录才能访问
.requestMatchers(HttpMethod.GET, "/api/orders/**").authenticated()

// 需要特定角色
.requestMatchers("/api/admin/**").hasRole("ADMIN")
.requestMatchers(HttpMethod.PUT, "/api/rentals/**").hasAnyRole("ADMIN", "CS")
```

### 4.5 前端认证配合

前端通过 Axios 请求拦截器，在每个请求中自动附加 token：

```typescript
// api/http.ts
http.interceptors.request.use((config) => {
  const token = localStorage.getItem('auth_token');
  if (token) {
    config.headers.Authorization = `Bearer ${token}`;
  }
  return config;
});

// 响应拦截器：收到 401 时自动清除登录状态并跳转登录页
http.interceptors.response.use(
  (response) => response,
  (error) => {
    if (error.response?.status === 401) {
      useAuthStore().logout();
      router.push('/login');
    }
  }
);
```

前端路由守卫在每次页面跳转前检查权限：

```typescript
// router/index.ts
router.beforeEach((to, _from, next) => {
  const auth = useAuthStore();
  const { requireAuth, roles } = to.meta;

  // 需要登录但没 token → 跳转登录页
  if (requireAuth && !auth.isLoggedIn) {
    next({ name: 'login', query: { redirect: to.fullPath } });
    return;
  }

  // 需要特定角色但角色不匹配 → 跳转首页
  if (roles?.length > 0 && !roles.includes(auth.user.role)) {
    next({ name: 'portal' });
    return;
  }

  next();
});
```

## 五、核心设计二：订单状态机

### 5.1 状态流转规则

订单生命周期由严格的状态机控制，所有状态变更都必须经过合法性校验：

```
用户下单
   │
   ▼
┌─────────────────┐   客服确认    ┌─────────────────┐   租赁完成    ┌─────────────────┐
│ WAITING_CONFIRM │ ───────────→ │   IN_PROGRESS   │ ───────────→ │    COMPLETED    │
│    (待确认)      │              │     (进行中)      │              │     (已完成)     │
└────────┬────────┘              └────────┬────────┘              └────────┬────────┘
         │                                │                                │
         │ 用户取消                        │ 用户取消                        │ 用户申请售后
         ▼                                ▼                                ▼
┌─────────────────┐              ┌─────────────────┐              ┌─────────────────┐
│    CANCELLED    │              │    CANCELLED    │              │   AFTER_SALE    │
│    (已取消)      │              │    (已取消)      │              │    (售后中)      │
└─────────────────┘              └─────────────────┘              └─────────────────┘
```

### 5.2 状态校验实现

状态流转的合法性校验在 `OrderService.isValidTransition()` 中实现：

```java
private boolean isValidTransition(String from, String to) {
    // 除已完成和已取消外，任何状态都可以取消
    if ("CANCELLED".equals(to) && !"COMPLETED".equals(from) && !"CANCELLED".equals(from)) {
        return true;
    }
    // 状态机：每个状态只能转到特定的目标状态
    return switch (from) {
        case "WAITING_CONFIRM" -> "IN_PROGRESS".equals(to) || "CANCELLED".equals(to);
        case "IN_PROGRESS"     -> "COMPLETED".equals(to)    || "CANCELLED".equals(to);
        case "COMPLETED"       -> "AFTER_SALE".equals(to);
        default -> false;
    };
}
```

**设计要点**：
- 使用 Java 14+ 的 switch 表达式，代码简洁清晰
- 已完成的订单不能取消（只能进入售后）
- 已取消的订单不能再次操作
- 任何非法的状态变更都会抛出异常，Controller 层捕获后返回错误信息

### 5.3 订单创建的业务校验

`OrderService.create()` 在创建订单时执行多重校验：

```java
public RentalOrder create(Long userId, Long productId, Integer rentHours, ...) {
    // 校验1：租赁时长必须大于 0
    if (rentHours < 1) throw new IllegalArgumentException("租赁时长必须大于 0");

    // 校验2：商品必须存在且状态为 AVAILABLE
    RentalProduct product = productMapper.findById(productId);
    if (!"AVAILABLE".equals(product.getStatus())) throw ...;

    // 校验3：防重复下单（该用户对该商品无进行中的订单）
    if (orderMapper.countActiveByUserAndProduct(userId, productId) > 0) throw ...;

    // 计算金额
    BigDecimal amount = product.getPrice().multiply(BigDecimal.valueOf(rentHours));

    // 生成订单号（DR + 时间戳，保证唯一性）
    order.setOrderNo("DR" + System.currentTimeMillis());

    // 初始状态
    order.setStatus("WAITING_CONFIRM");
}
```

防重复下单的 SQL 查询：

```sql
SELECT COUNT(*) FROM rental_order
WHERE user_id = #{userId}
  AND product_id = #{productId}
  AND status IN ('WAITING_CONFIRM', 'IN_PROGRESS')
```

只有待确认和进行中的订单才算"活跃"，已完成或已取消的不影响再次下单。

## 七、核心设计四：统一 API 响应封装

### 7.1 ApiResponse 结构

所有后端接口返回统一的 JSON 格式：

```json
{
  "success": true,
  "message": "操作成功",
  "data": { ... }
}
```

对应的 Java 类：

```java
public class ApiResponse<T> {
    private final boolean success;
    private final String message;
    private final T data;

    public static <T> ApiResponse<T> success(String message, T data) {
        return new ApiResponse<>(true, message, data);
    }

    public static <T> ApiResponse<T> fail(String message) {
        return new ApiResponse<>(false, message, null);
    }
}
```

使用泛型 `<T>` 使得 `data` 字段可以是任意类型（Map、List、对象等），保持类型安全。

### 7.2 全局异常处理

Controller 层通过 try-catch 捕获 Service 层抛出的异常，转换为统一的错误响应：

```java
@PostMapping("/api/orders")
public ApiResponse createOrder(@RequestBody Map<String, Object> body, HttpServletRequest request) {
    try {
        Long userId = JwtUtil.getUserId(extractToken(request));
        RentalOrder order = orderService.create(userId, ...);
        return ApiResponse.success("下单成功", order);
    } catch (IllegalArgumentException e) {
        return ApiResponse.fail(e.getMessage());  // 业务异常 → 返回错误信息
    }
}
```

## 八、核心设计五：前端状态管理

### 8.1 Pinia 状态管理

使用 Pinia（Vue 3 推荐的状态管理库）管理全局认证状态：

```typescript
// stores/auth.ts
export const useAuthStore = defineStore('auth', () => {
  const token = ref<string | null>(localStorage.getItem('auth_token'));
  const user = ref<UserInfo | null>(null);

  // 计算属性：角色判断
  const isLoggedIn = computed(() => !!token.value && !!user.value);
  const isAdmin = computed(() => user.value?.role === 'ADMIN');

  // 登录：保存 token 和用户信息到 localStorage
  function setAuth(newToken: string, newUser: UserInfo) {
    token.value = newToken;
    user.value = newUser;
    localStorage.setItem('auth_token', newToken);
    localStorage.setItem('auth_user', JSON.stringify(newUser));
  }

  // 退出：清除所有状态
  function logout() {
    token.value = null;
    user.value = null;
    localStorage.removeItem('auth_token');
    localStorage.removeItem('auth_user');
  }
});
```

**为什么用 localStorage 持久化？** 刷新页面时 Vue 应用会重新初始化，内存中的状态会丢失。存到 localStorage 后，刷新页面时可以从 localStorage 恢复登录状态。

### 8.2 路由懒加载

所有页面组件都使用动态 import 实现懒加载：

```typescript
const PortalView = () => import('@/views/PortalView.vue');
const AdminDashboardView = () => import('@/views/AdminDashboardView.vue');
```

配合 Vite 的手动分包策略，首屏只加载必要的代码，后台管理等低频页面按需加载：

## 九、核心设计六：前后端连接

### 9.1 Vite 开发代理

开发时前端运行在 5173 端口，后端在 8080 端口，存在跨域问题。通过 Vite 的代理配置解决：

```typescript
// vite.config.ts
server: {
  port: 5173,
  proxy: {
    '/api': {
      target: 'http://localhost:8080',
      changeOrigin: true
    }
  }
}
```

前端发 `/api/auth/login` 请求时，Vite 开发服务器会自动转发到 `http://localhost:8080/api/auth/login`，对前端代码完全透明。

### 9.2 MyBatis 数据访问

Mapper 层使用 MyBatis 注解方式编写 SQL，无需 XML 映射文件：

```java
@Mapper
public interface RentalOrderMapper {

    @Insert("""
        INSERT INTO rental_order(order_no, user_id, product_id, unit_price, ...)
        VALUES(#{orderNo}, #{userId}, #{productId}, #{unitPrice}, ...)
        """)
    @Options(useGeneratedKeys = true, keyProperty = "id")
    int insert(RentalOrder order);

    @Select("SELECT * FROM rental_order WHERE id = #{id}")
    RentalOrder findById(Long id);
}
```

**`#{}` 占位符**：MyBatis 会自动处理参数绑定和 SQL 注入防护，等价于 PreparedStatement 的 `?`。

**联表查询示例**（订单详情需要关联用户和商品信息）：

```sql
SELECT o.order_no, o.status, o.order_amount,
       COALESCE(u.nickname, u.username) AS buyer,
       p.name AS item
FROM rental_order o
LEFT JOIN sys_user u ON o.user_id = u.id
LEFT JOIN rental_product p ON o.product_id = p.id
WHERE o.order_no = #{orderNo}
```

## 十一、关键设计决策总结

| 设计决策 | 技术方案 | 为什么这样选 |
|----------|----------|-------------|
| 用户认证 | JWT + Spring Security | 无状态，适合前后端分离，天然支持分布式 |
| 密码存储 | BCrypt 单向哈希 | 不可逆，即使数据库泄露也无法还原密码 |
| 密码改后 token 失效 | pwdUpdatedAt 版本校验 | 解决 JWT 签发后无法主动撤销的问题 |
| 权限控制 | RBAC 三表设计 | 用户-角色多对多，灵活可扩展 |
| 订单状态 | 状态机模式 | 严格控制状态流转，防止非法操作 |
| 防重复下单 | 查询活跃订单 | 同一用户对同一商品不能有多个进行中的订单 |
| 价格快照 | 订单存下单时价格 | 商品改价不影响历史订单 |
| API 响应 | 统一 ApiResponse 封装 | 前端解析逻辑统一，错误处理一致 |
| 数据访问 | MyBatis 注解 SQL | 轻量、直观，适合中小型项目 |
| 前端状态 | Pinia + localStorage | 响应式 + 持久化，刷新不丢状态 |
| 跨域解决 | Vite 开发代理 | 开发环境透明代理，生产环境同源部署 |
| 组件加载 | 路由懒加载 + 手动分包 | 首屏加载快，后台代码按需加载 |
