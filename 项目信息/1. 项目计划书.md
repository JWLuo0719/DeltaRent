## 一、项目概述

### 1. 项目背景
“三角洲行动”相关玩家群体围绕账号租赁、账号展示、订单咨询、售后申诉等场景，存在较高频的信息撮合需求。当前大量交易流程仍依赖微信群、QQ群、人工客服和零散表单完成，普遍存在以下问题：

- 价格规则不透明，人工报价效率低
- 订单进度依赖人工同步，信息容易遗漏
- 账号资源构成、租用时段、履约记录缺乏统一管理
- 售后处理、申诉记录、运营统计难以沉淀
- 业务流程高度依赖个人经验，不利于后续扩展

参考现有同类站点，可以抽象出其共同核心能力：商品展示、账号租赁、订单中心、公告客服、后台运营管理。本项目拟围绕这些高频能力，设计并实现一个面向课程实践的完整信息系统，以网站形式呈现，形成“前台业务展示 + 后台运营管理 + 订单流程闭环”的可运行原型。

考虑到课程时间、团队技术水平与实现成本，本项目将系统定位为“商用级原型”而非直接投入真实交易的生产系统：

- 一期目标是做出可演示、可运行、业务闭环完整的课程系统
- 设计上保留前后端分离、角色权限、异步解耦、配置化规则等可扩展能力
- 对真实支付、短信、自动上号、风控接口、对象存储等重型能力仅预留接口，不在课程一期强行落地

因此，本项目既满足课程对信息系统完整性的要求，也能为后续继续升级为更真实的商业系统提供架构基础。

### 2. 项目目标
本项目计划实现一个以“账号租赁”为核心业务的网站系统，目标如下：

- 完成一个可运行、可演示、业务流程完整的信息系统原型
- 采用前后端分离架构，形成较清晰的前台与后台边界
- 支持用户注册登录、商品浏览、订单提交、订单跟踪、后台审核、公告管理、数据统计等完整业务闭环
- 通过角色权限控制、状态流转管理、操作日志、配置化价格规则等机制，体现信息系统的规范性
- 在保证课程可完成性的前提下，预留异步消息、分布式拆分、支付接入、风控扩展等后续升级空间
- 形成与课程考核一致的过程文档、设计文档、测试材料与 Git 留痕证据

本项目的一期验收目标不是“做大而全”，而是“核心链路真实、技术路线合理、原型质量较高、后续升级明确”。

### 3. 开发环境与条件
结合课程周期、团队协作效率和后续扩展需求，拟采用“模块化单体后端 + 前后端分离 + 事件异步化预留”的技术路线。

| 类别 | 方案 |
| --- | --- |
| 前端 | Vue 3 + TypeScript + Vite + Vue Router + Pinia + Element Plus |
| 后端 | Java 17 + Spring Boot 3 + Spring Security + JWT + MyBatis-Plus |
| 数据库 | MySQL 8.0 |
| 缓存/会话 | Redis |
| 异步解耦 | 先采用事件表 / 任务队列思路实现，后续可平滑升级到 RabbitMQ |
| 接口文档 | Apifox 或 Swagger / OpenAPI |
| 原型/设计 | draw.io、ProcessOn、Figma 或墨刀 |
| 版本管理 | Git + Gitee / GitHub |
| 运行环境 | Windows / Linux，Node.js 20+，JDK 17，MySQL 8，Redis 7 |

说明：

- 课程一期优先保证“能开发、能联调、能演示”，因此后端不直接上微服务，而采用模块化单体架构
- 通过领域模块拆分、统一接口规范、订单事件模型等方式，为后续微服务拆分保留空间
- 非核心链路如消息通知、日志汇总、统计更新等采用异步化思路，避免所有业务逻辑强耦合在主事务中

### 4. 项目简介
本项目面向“三角洲行动”账号租赁场景，建设集账号展示、资源说明、订单下单、售后申诉、后台运营于一体的管理系统，以账号为核心商品统一管理号内哈夫币、装备与仓库资源。

### 5. 核心技术简介
项目采用 Vue 3 + TypeScript + Vite 构建前端，Spring Boot 3 + Spring Security + JWT + MyBatis-Plus 构建后端，结合 MySQL 与 Redis 实现账号、订单、权限与统计管理，并预留异步扩展能力。

## 二、需求分析

### 1. 目标用户与使用场景
本系统面向四类核心用户：

| 用户角色 | 主要诉求 | 典型场景 |
| --- | --- | --- |
| 游客 | 了解平台业务、查看商品与公告 | 浏览首页、查看账号租赁列表、了解租赁说明 |
| 普通用户 | 浏览账号、提交租赁订单、查看进度 | 查看账号详情、选择租赁时长、查看订单状态 |
| 客服/审核员 | 审核订单、处理履约与售后 | 处理订单确认、推进订单状态、处理申诉 |
| 运营/管理员 | 维护账号、价格、公告、统计与权限 | 管理商品、配置价格规则、查看经营数据 |

系统主要使用场景如下：

1. 用户浏览前台页面，查看平台公告、业务规则、热门账号与参考价格
2. 用户注册登录后浏览账号详情，查看号内哈夫币、装备、仓库资源等信息
3. 用户选择合适账号与租赁时长提交订单，并在订单中心查看租赁状态
4. 客服在后台处理订单确认、派单、订单状态推进和售后申诉
5. 运营在后台管理账号商品、价格规则、公告内容、用户数据和经营数据

### 2. 核心功能清单
为确保课程一期可顺利完成，同时又具备较强展示效果，功能范围采用“核心必做 + 扩展预留”的方式规划。

#### 2.1 一期核心功能

**前台门户功能**

- 首页展示：平台介绍、公告通知、业务入口、常见问题
- 商品展示：账号列表、标签筛选、详情查看、价格展示
- 租赁说明：租赁规则、账号资源说明、价格影响因素说明
- 用户认证：注册、登录、退出、个人资料维护

**账号租赁业务**

- 账号发布与库存管理
- 账号详情展示
- 账号资源信息维护（哈夫币、装备、仓库资源等）
- 订单创建与租赁时长选择
- 订单状态跟踪
- 租赁结束与归还记录
- 评价/申诉入口

**订单与售后功能**

- 订单中心：查看全部订单、筛选、详情页
- 订单状态流转：待审核、待确认、进行中、已完成、已取消、售后中
- 售后申诉：提交问题、客服处理、处理结果记录
- 消息通知：订单状态变化、审核结果、公告提醒

**后台管理功能**

- 用户管理
- 角色权限管理
- 商品与账号管理
- 账号租赁订单管理
- 公告内容管理
- 价格规则管理
- 数据看板与基础统计
- 操作日志与审计记录

#### 2.2 二期扩展功能预留

- 接入真实支付能力
- 接入短信/邮件通知
- 引入对象存储管理截图与附件
- 引入消息队列处理通知、统计、日志汇总
- 增加风控规则引擎、黑名单、频率限制
- 增加邀请码、分销返佣、优惠券等营销能力
- 增加移动端适配或小程序版本

#### 2.3 主要业务流程

**流程一：账号租赁**

1. 用户浏览账号列表并查看详情
2. 系统展示账号内哈夫币、装备、仓库资源、可租时长与价格信息
3. 用户选择租赁时长并提交租赁订单
4. 平台确认账号库存、可租时段与订单信息
5. 客服完成订单确认与派单，订单进入进行中状态
6. 租赁结束后记录归还结果与履约状态
7. 用户可发起评价或售后申诉

**流程二：后台运营管理**

1. 管理员维护账号商品、资源说明、价格规则、公告内容
2. 客服处理订单审核、派单与售后申诉
3. 系统同步更新统计数据与操作日志
4. 运营通过看板了解订单量、完成率、热门账号等指标

### 3. 非功能需求
除业务功能外，本项目还需满足以下非功能需求。

#### 3.1 性能要求

- 常见页面查询响应时间控制在 2 秒以内
- 课程演示场景下支持 50 至 100 并发访问的基础能力
- 核心订单创建操作具备较稳定的响应表现
- 列表查询支持分页、筛选与条件检索，避免一次性加载过多数据

#### 3.2 安全要求

- 采用 JWT + Spring Security 实现身份认证
- 采用 RBAC 实现角色权限控制
- 密码使用加密存储，不明文保存敏感信息
- 对订单状态流转、关键配置变更、审核操作保留审计日志
- 对上传文件进行格式限制与基本校验
- 对表单输入进行合法性校验，防止常见注入与越权风险

#### 3.3 兼容性要求

- 支持 Chrome、Edge 等主流现代浏览器
- 页面优先适配 1366px 及以上桌面端分辨率
- 前台页面兼顾平板与移动端基础浏览体验
- 后台管理系统优先保障 PC 端操作效率

#### 3.4 可维护性与扩展性要求

- 前后端分离，接口清晰，便于独立开发与联调
- 业务模块按领域拆分，降低后期重构成本
- 核心业务流程采用状态机/状态枚举设计，便于后续扩展
- 非核心任务通过异步事件处理，便于未来接入消息中间件
- 保持代码、接口文档、数据库设计与测试材料同步维护

#### 3.5 合规与课程边界说明

- 本项目为课程原型系统，不直接对接真实支付与真实游戏自动化控制
- 系统演示以模拟数据和内部测试流程为主
- 业务设计重点体现信息系统分析、设计、实现与管理能力

## 三、技术路线

### 1. 总体架构
本项目采用“前后端分离 + 模块化单体 + 异步解耦预留”的总体架构。

```text
┌──────────────────────────────┐
│        前台门户 Web          │
│  首页 / 商品 / 租赁 / 订单    │
└──────────────┬───────────────┘
               │ HTTP / JSON
┌──────────────▼───────────────┐
│         后台管理 Web          │
│ 用户 / 账号 / 订单 / 公告 / 统计 │
└──────────────┬───────────────┘
               │
┌──────────────▼──────────────────────────────────────────┐
│                  Spring Boot 后端服务                   │
│ 认证授权 | 用户中心 | 商品管理 | 账号租赁订单 | 售后申诉    │
│ 公告管理 | 价格规则 | 统计分析 | 日志审计                │
└──────────────┬───────────────────────┬──────────────────┘
               │                       │
        ┌──────▼──────┐         ┌──────▼──────┐
        │   MySQL      │         │    Redis     │
        │ 业务数据持久化 │         │ 缓存/会话/热点数据 │
        └──────┬──────┘         └─────────────┘
               │
        ┌──────▼──────────────────────────────────┐
        │ 事件表 / 异步任务 / MQ 接口预留          │
        │ 通知推送 / 日志汇总 / 统计更新 / 消息中心 │
        └─────────────────────────────────────────┘
```

该架构的核心考虑如下：

- 一期采用模块化单体，降低部署和调试复杂度，适合课程项目推进
- 从业务边界上拆分出用户、商品、订单、配置、统计等领域模块，为后续拆服务做准备
- 对通知、消息、审计、统计等非核心流程采用异步事件设计，避免系统过度耦合
- 同时提供前台门户和后台管理两个入口，体现完整信息系统形态

### 2. 主要技术

#### 2.1 前端技术方案

- 使用 Vue 3 + TypeScript 搭建前端工程，提高组件复用性与类型安全
- 使用 Vite 构建开发环境，提升开发效率
- 使用 Vue Router 管理页面路由
- 使用 Pinia 管理用户信息、菜单权限、订单查询条件等前端状态
- 使用 Element Plus 快速构建后台界面和表单页面
- 使用 Axios 对接后端 RESTful API
- 使用 ECharts 实现后台统计图表

前台与后台可以采用同一技术栈下的双端页面结构，也可视时间情况拆成两个前端工程，但保持统一接口规范。

#### 2.2 后端技术方案

- 使用 Spring Boot 3 构建 RESTful API 服务
- 使用 Spring Security + JWT 实现认证授权
- 使用 MyBatis-Plus 简化数据访问与基础 CRUD
- 使用统一返回结构、全局异常处理、参数校验，规范接口行为
- 使用分层结构组织代码：Controller、Service、Mapper、Domain、DTO/VO
- 使用操作日志、状态变更记录和审计字段加强系统可追踪性

#### 2.3 数据与缓存方案

- MySQL 负责用户、商品、订单、公告、日志等核心业务数据持久化
- Redis 用于验证码/会话缓存、热点数据缓存、幂等控制或限流预留
- 价格规则与字典配置采用表驱动方式管理，便于后续运营维护

#### 2.4 异步解耦与扩展方案

为兼顾课程可实现性和后续升级空间，本项目不在一期直接拆分成分布式微服务，而采用“先抽象、后拆分”的策略：

- 一期通过事件表、异步任务或消息接口抽象，处理消息通知、统计更新、操作留痕等非核心链路
- 二期可平滑替换为 RabbitMQ 等消息中间件
- 一期以单库为主，二期可按订单、库存、用户等领域拆分服务和数据库
- 一期保留对象存储、支付接口、短信接口等适配层，后期可直接替换实现

#### 2.5 工程化方案

- Git 进行版本管理，按阶段打 Tag
- 使用统一命名规范与提交规范，确保课程过程材料可追溯
- 接口文档与数据库设计同步存放在仓库中
- 后续可增加单元测试、接口测试与部署脚本，提高系统完整度

### 3. 数据设计初步考虑
本系统数据设计围绕“用户、账号、订单、规则、日志”五类核心对象展开。

#### 3.1 主要实体

- 用户（User）
- 角色（Role）
- 权限菜单（Permission / Menu）
- 账号商品（AccountProduct）
- 账号租赁订单（AccountRentalOrder）
- 价格规则（PriceRule）
- 公告信息（Notice）
- 售后申诉（Appeal）
- 订单事件记录（OrderEvent）
- 操作日志（OperationLog）

#### 3.2 关键数据关系

- 一个用户可以拥有多个订单
- 一个账号商品可以产生多个租赁订单
- 一个租赁订单对应多条状态变更记录
- 一个订单可以关联多条售后记录、日志记录和通知记录
- 用户与角色之间为多对多关系

#### 3.3 主要数据表初步设计

| 表名 | 说明 |
| --- | --- |
| `sys_user` | 用户基础信息 |
| `sys_role` | 角色信息 |
| `sys_user_role` | 用户角色关联 |
| `sys_menu` | 菜单与权限点 |
| `account_product` | 账号商品信息 |
| `account_product_image` | 商品展示图 |
| `account_rental_order` | 账号租赁订单 |
| `order_event` | 订单状态流转记录 |
| `price_rule` | 价格规则配置 |
| `notice` | 公告与资讯内容 |
| `appeal_record` | 售后申诉记录 |
| `operation_log` | 后台操作日志 |
| `message_record` | 站内消息与通知记录 |

#### 3.4 数据设计原则

- 表结构遵循“一表一责”，避免过度混用
- 核心订单表统一保留创建人、创建时间、更新时间、状态字段
- 对价格规则、标签、状态枚举等尽量采用配置化设计
- 为后续数据分析预留统计维度，如订单金额、完成率、账号分类、来源渠道等

## 四、进度安排

### 1. 阶段划分
项目按“计划书阶段 - 设计阶段 - 开发阶段 - 联调测试阶段 - 结项交付阶段”推进。

#### 第一阶段：项目规划与需求分析

- 明确选题方向与业务边界
- 竞品参考与功能抽象
- 完成项目计划书
- 确定技术栈与仓库结构

#### 第二阶段：系统设计与原型输出

- 细化功能清单与业务流程
- 绘制系统架构图、业务流程图、E-R 图
- 输出 UI 原型和接口草案
- 确定数据库初版设计

#### 第三阶段：基础框架与核心模块开发

- 完成前后端项目初始化
- 完成登录认证、权限管理、用户中心
- 完成商品管理、公告管理、基础配置管理
- 完成数据库建表与基础接口联调

#### 第四阶段：核心业务开发

- 完成账号租赁流程
- 完成订单中心、售后申诉、状态流转
- 完成后台审核、订单处理、数据看板

#### 第五阶段：联调优化与测试

- 完成前后端整体联调
- 补充接口测试、功能测试与异常测试
- 优化页面交互、数据校验与日志记录
- 补齐中期/结项文档与演示素材

#### 第六阶段：结项整理与答辩准备

- 补全软件说明书与用户手册

### 2. Git协作方式
为满足课程考核对个人工作量和过程留痕的要求，项目采用规范化 Git 协作方式。

#### 2.1 仓库与分支策略

- 建立统一远端仓库，所有成员使用同一仓库协作
- `main` 分支用于稳定版本与阶段提交
- `dev` 分支用于日常集成开发
- `feature/xxx` 分支用于个人功能开发，如 `feature/login`、`feature/account-rental-order`

#### 2.2 提交规范

- 每次提交必须写清楚实际内容，不使用 `update`、`test` 等无意义说明
- 推荐提交格式如下：

```text
feat(auth): 完成登录与JWT认证
feat(rental): 新增账号租赁订单提交接口
docs(plan): 完善项目计划书
test(order): 补充订单状态流转测试用例
fix(product): 修复商品分页查询问题
```

#### 2.3 阶段标签

- `v1-plan`：项目计划书阶段
- `v2-design`：中期设计阶段
- `v3-final`：最终验收阶段

#### 2.4 建议仓库目录

```text
docs/
  plan/
  design/
  test/
  meeting/
  report/
  api/

sql/
src/
  server/
  web/

ui/
```

这样可以保证代码、文档、测试、会议记录都能在仓库中形成版本化证据，符合课程评分要求。
